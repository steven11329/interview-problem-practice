# 13. Roman to Integer - 解法分析

## basic.ts 的除錯過程

**最初版本的 bug**

用 `Map` 查表,再用 `next <= current * 10` 來判斷是否為「減法組合」,但這個條件寫反了:

- 對「降序」(正常疊加,如 L 接 V)幾乎必為真,誤觸發減法分支
- 對「升序」(真正的減法組合,如 I 接 V)算式寫成 `current - next`,符號也反了

實測結果:`LVIII` 算出 `48`(應為 `58`),`IV`、`IX`、`XL` 全部算出負數。

**修正方向**

判斷條件應該只看「目前符號是否小於下一個符號」:

- 是 → 目前符號要被減去(例如 IV 裡的 I)
- 否 → 正常相加

修正後改用「往後看一格、看不到就當作 0」的寫法,不再需要手動 `i += 1` 跳位、也不用另外處理陣列尾端的邊界判斷,程式碼從 22 行縮到 8 行。

**驗證方式**:寫一個 `intToRoman` 當 oracle,窮舉 1~3999(題目保證的合法範圍)所有羅馬數字丟進去比對,全數通過。

---

## basic.ts - Map 查表 + 往後看一格

**做法**
1. 用 `Map<string, number>` 存符號對應的數值
2. 遍歷字串,往後看一格:若目前符號值 < 下一個符號值,代表是減法組合,計入負值;否則正常相加

**複雜度**
- 時間:O(n)
- 空間:O(1)(Map 固定 7 個 entry,不隨輸入成長)

**缺點**
- 每次呼叫 `romanToInt` 都會重新 `new` 一個 `Map`,即使內容固定不變,也會產生額外的記憶體配置與雜湊表結構開銷

---

## improved.ts - switch 查表(降低記憶體開銷)

**做法**
- 把 `Map` 換成獨立的 `valueOf(symbol)` 函式,用 `switch` 直接回傳數值
- 主邏輯與 `basic.ts` 相同(往後看一格、比較大小)

**複雜度**
- 時間:O(n)
- 空間:O(1),且不像 Map 版本會在每次呼叫時配置雜湊表

**優點**
- 不需要建立任何資料結構,只用到幾個基本型別變數,記憶體佔用更小
- `switch` 是編譯期就能決定分支的查表,查找成本也更低

---

## alternative.ts - 由右往左掃描 + 記錄目前最大值

**做法**
1. 維護 `prevMax`(從右邊往左看,目前為止看過的最大符號值)
2. 從字串尾端往前遍歷:
   - 若目前符號值 < `prevMax`,代表它是被減去的(例如 IV 裡的 I),計入負值
   - 否則正常相加,並更新 `prevMax`

**複雜度**
- 時間:O(n)
- 空間:O(1)

**正確性原理**
- 羅馬數字裡,會被減去的符號一定比它右邊那個符號小(這是題目本身的規則,如 IV、IX、XL 等六種組合皆是小符號在大符號前面)
- 由右往左走,只要目前符號比「右邊已經出現過的最大符號」還小,就一定是被減去的那個,不需要額外往後多看一格、也不用處理陣列越界

**與 basic.ts / improved.ts 的差異**
- 概念上更貼近「羅馬數字本質是從大到小排列,例外才減」這個描述
- 不需要 `i + 1 < s.length` 這種越界檢查,邏輯上更省一個條件分支

## 結論

| | basic.ts | improved.ts | alternative.ts |
|---|---|---|---|
| 掃描方向 | 由左往右 | 由左往右 | 由右往左 |
| 查表方式 | Map(每次呼叫重建) | switch | switch |
| 時間複雜度 | O(n) | O(n) | O(n) |
| 空間複雜度 | O(1)(但有 Map 配置開銷) | O(1) | O(1) |

三者都能通過題目範例與 1~3999 窮舉測試。若在意記憶體開銷,`improved.ts` 或 `alternative.ts` 都比最初的 `basic.ts`(Map 版)更輕量;`alternative.ts` 額外省去了「往後看一格」需要的越界判斷。
