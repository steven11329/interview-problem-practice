# 169. Majority Element - 解法分析

## basic.ts - 雜湊表計數法

**做法**
1. 用 `Map<number, number>` 記錄每個元素出現的次數
2. 遍歷所有 entries,找出出現次數最多的元素

**複雜度**
- 時間:O(n)
- 空間:O(n)(最差情況下,陣列中有接近 n/2 種不同的元素都要存進 Map)

**優點**
- 邏輯直覺,容易理解與驗證
- 不需要事先知道「多數元素一定存在」這個前提,也能找出出現次數最多的元素(可延伸用來解「找出現最多次的元素」這種更一般的題目)

**缺點**
- 額外使用 O(n) 空間存 Map,不符合題目 follow-up 的 O(1) 空間要求
- 需要遍歷兩次(建表一次、找最大值一次),雖然仍是 O(n),但實務上常數較大

**曾出現的 bug**
- 一開始在找最大值的迴圈中,只更新了 `maxN` 卻忘記同步更新 `max`,導致 `max` 永遠停留在初始值 0,最終結果變成「Map 迭代順序中最後一個出現過的元素」而非「出現次數最多的元素」。已修正為在 `if (max < m)` 成立時同時更新 `max = m; maxN = n;`。

## improved.ts - Boyer-Moore 投票算法

**做法**
1. 維護一個 `candidate`(目前候選的多數元素)與 `count`(信心計數)
2. 遍歷陣列:元素與 candidate 相同就 `count++`,不同就 `count--`
3. `count` 歸零時,把下一個元素設為新的 candidate
4. 遍歷結束後 candidate 即為答案

**複雜度**
- 時間:O(n)
- 空間:O(1)(只用兩個變數,不需要額外資料結構)

**正確性原理**
- 若某元素出現次數 > ⌊n/2⌋,代表它出現的次數比其他所有元素加起來還多
- 可以把「多數元素」想成 +1 票、「其他任何元素」想成 -1 票,不管怎麼互相抵銷,總票數加總必為正,所以多數元素一定能在抵銷後存活成為最終 candidate

**優點**
- 完全符合題目 follow-up 的 O(1) 空間、O(n) 時間要求
- 只需遍歷一次陣列,常數更小

**缺點**
- **前提依賴題目保證「多數元素一定存在」**。如果陣列中不保證有出現次數 > n/2 的元素,這個算法找出來的 candidate 不一定正確(需要額外再跑一次驗證 candidate 出現次數是否真的 > n/2)
- 相較 `basic.ts`,程式邏輯較不直覺,第一次看不容易理解「票數抵銷」的概念

---

## 結論

| | basic.ts | improved.ts |
|---|---|---|
| 時間複雜度 | O(n) | O(n) |
| 空間複雜度 | O(n) | O(1) |
| 前提假設 | 無 | 依賴「多數元素必存在」 |
| 可讀性 | 高 | 中(需理解投票抵銷概念) |

兩者都能通過題目給的兩組範例測試。若題目情境保證多數元素存在(如本題),優先選 `improved.ts`;若情境不保證,或想順便找出「出現最多次的元素」而非嚴格定義的多數元素,`basic.ts` 的雜湊表法更泛用、更安全。
